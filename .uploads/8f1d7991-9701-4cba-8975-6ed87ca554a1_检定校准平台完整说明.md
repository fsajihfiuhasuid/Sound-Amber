## 一、平台定位

### 1.1 目标

将检定校准中与仪器无关的业务抽成公共平台，把紫外、原吸及其他仪器的差异放在插件和外部适配器中。

公共业务包括标准物、规程、模板、任务、测量规划、执行状态、人工确认、设备回执、计算结果及运行记录。平台组织这些业务，不重新实现底层仪器通信、采集驱动或计量算法。

接入一种新仪器时，原则上增加该仪器的业务定义和外部适配，不复制整个检定校准系统，也不在公共代码中堆积 `UV/AA/其他仪器` 条件分支。

### 1.2 三方分工

| 责任方 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 公共平台 | 统一业务对象、规划、状态推进、接口入口、插件选择、公共表及 JDBC 仓储 | 仪器通信协议、算法公式、现场数据库部署与安全联锁 |
| 仪器插件 | 描述本仪器的方法、参数、规程、标准物要求、步骤和模板；接入已有驱动及算法 | 重写公共状态机、复制公共 WebSocket Handler、提供默认成功的假驱动 |
| 宿主项目及仪器团队 | 真实驱动和算法、仓储与事务、认证授权、证据归档、部署和现场安全 | 用测试替身代替正式实现或以软件日志代替安全确认 |

**算法和驱动仍然外接。** 插件只把已有能力转换为平台认识的接口，不要求把这些能力重新写一遍。

### 1.3 当前采用什么编排方式

当前是 Java 业务状态机配合短步骤编排，没有引入 LiteFlow，也没有可视化流程编辑器。

`MeasurementOrchestrator` 是短步骤编排接口。自动配置在宿主没有提供该类型 Bean 时装配默认顺序编排器，版本为 `metrology.plugin.sequence@1`；一次调用执行计划复核和一次设备提交，不等待人工确认、不后台轮询，也不自动推进下一项目。

宿主现在可以注入自定义 `MeasurementOrchestrator` Bean，不必修改公共自动配置。必须提供固定版本，并在当前线程内先执行 `verifyPlan()`、后执行 `submitMeasurement()`，且只能提交一次。公共状态机仍校验顺序和完整性；重复未选定的编排器或空版本会拒绝装配。此扩展只作用于公共业务插件，紫外兼容运行时不经过它；单独增加 LiteFlow 等依赖不会自动完成接入。

## 二、当前实现范围

### 2.1 两种插件、两条路径

```text
紫外兼容路径
  原紫外页面与 0..5/close 协议
    → 公共 WebSocket 入口
    → 完整紫外兼容插件
    → 紫外分层流程
    → 公共工作区业务服务与可替换适配器
    → 原驱动、原算法、原模板和原存储服务

新仪器公共业务路径
  对接公共接口的前端
    → 公共 REST/WebSocket 入口
    → 业务插件
    → 公共规划与执行状态机
    → 仪器团队已有驱动、算法及宿主仓储
```

| 项目 | 紫外兼容插件 | 新仪器业务插件 |
| --- | --- | --- |
| 接口类型 | `CompatibilityInspectionPlugin` | `BusinessInspectionPlugin` |
| 日志类型 | `COMPATIBILITY` | `SHARED_BUSINESS` |
| 执行运行时 | `FullUvInspectionRuntime` | `BusinessPluginRuntime` |
| 协议 | 保留紫外 `0..5/close` | `start/advance/confirm/poll/stop/status` |
| 标准物、模板和任务管理 | 继续使用原紫外管理服务和数据 | 使用公共业务对象及宿主仓储 |
| 执行状态 | 保留旧紫外线程、暂停和进程内状态 | 使用公共 `BusinessRun` 状态机 |
| 设备占用 | 不因此自动获得公共状态机的占用保障 | 要求宿主实现原子占用及修订号比较 |
| 停止语义 | 保留原停止分支，不能等同可靠空闲确认 | 停止后查询确认空闲才进入终态 |
| 建议用途 | 迁移和替代当前紫外入口 | 接入原吸及其他新仪器 |

**共享入口不等于共享全部执行保障。** 不能把公共业务状态机的持久化、防重或停止确认能力直接算到紫外兼容路径上。

└── README.md                   快速入口

### 3.1 公共核心的三层

公共包根为 `com.persee.workstation.metrology`。

| 包 | 职责 | 依赖原则 |
| --- | --- | --- |
| `domain` | 业务对象、版本引用、资源要求、状态及不变量 | 不依赖 Spring、具体仪器和数据库框架 |
| `application` | 组织业务用例：规划、复核、任务、运行推进 | 通过 `spi` 调用外部能力 |
| `spi` | 插件、驱动、算法、仓储、权限、通信和编排契约 | 由插件或宿主实现，不提供默认假成功 |

### 3.2 starter 和 uv

starter 包根为 `com.persee.workstation.metrology.boot`，是公共业务接入 Spring 宿主的装配层。

紫外包根为 `com.persee.workstation.uv_inexus.metrology.fulluv`，需要原紫外宿主中的服务和实体，不是可以脱离原项目直接运行的独立应用。

### 3.3 两种构建方式不要混淆

1. `metrology-extracted/pom.xml` 构建两个公共 JAR：core 和 starter，不构建紫外宿主。
2. 原紫外仓库根 `pom.xml` 通过 `build-helper-maven-plugin` 引入 core、starter、uv 的生产源码及 starter 资源，构建原紫外 Boot 应用。
3. 新仪器项目使用公共 JAR，再加入自己的正式插件，不需要引入原紫外应用和 uv 源码。
4. 新增 `instruments/aas` 文件夹不会自动变成当前聚合工程模块；需提供自己的 Maven 工程或显式配置构建关系。

### 3.4 `src/test` 和 `target`

`src/main` 才是生产实现。`src/test` 是自动回归，不进入生产 JAR；原吸示例和内存仓储只在这里验证平台是否脱离紫外及是否遵守业务契约。

`target` 是编译、测试和打包产物，可停止相关进程后删除并重新生成。不能把业务 `data`、模板、数据库文件或需要留存的现场日志当作构建缓存清理。

当前不再保留独立验证工程、一次性抽离工具、历史指纹基线、自定义构建脚本或 LiteFlow 试点目录。

## 四、业务对象与主要服务

### 4.1 不要混淆任务、计划和运行

```text
标准物 + 规程 + 模板
        ↓ 绑定实际仪器、选择标准物
InspectionTask：任务定义
        ↓ 查询设备能力、展开方法、解析资源
InspectionPlan：测量规划快照
        ↓ 编译人工确认/准备/采集步骤，固定插件及算法版本
ExecutableInspection：可执行定义
        ↓ start 创建一次运行
BusinessRun：运行状态、请求、结果和事件
```

| 对象 | 含义 | 不是 |
| --- | --- | --- |
| `ReferenceMaterial` | 标准物类别、证书引用、有效期、启用状态和标准值点 | 实际证书文件或已通过计量审核的证明 |
| `ReferenceValue` | 某定值点、数值条件及可选不确定度，显式携带单位 | 平台自动实现的单位换算 |
| `MaterialType` | 版本化类别结构、定值语义/单位、文本与枚举属性 | 所有仪器使用同一组固定属性 |
| `ResourceRequirement` | 类别、类型版本、点数、有效期、证书及指定属性要求 | 具体标准物选择或自动证书审核 |
| `ResourceBinding` | 项目和资源角色绑定到实际标准物 ID | 复制一份标准物数据 |
| `ProcedureVersion` | 版本化规程及有序项目定义 | 正在运行的任务 |
| `InspectionTemplate` | 模板版本、规程、不可变布局引用和渲染器版本 | 自带的任意 Excel/PDF 报告引擎 |
| `InspectionTask` | 实际仪器、规程版本和标准物绑定 | 已经开始测量的运行 |
| `InspectionPlan` | 仪器能力、资源和展开后的采集需求快照 | 永久有效的执行许可 |
| `ItemWorkflow` | 单项目的步骤、配方、算法和判定规则引用 | 驱动和算法的具体实现 |
| `DeviceOperation` | 带唯一请求身份的实际设备操作 | 已完成的测量结果 |
| `ItemCalculation` | 当前项目记录组成的外部计算请求 | 平台内部计算公式 |
| `BusinessRun` | 一次运行的版本、状态、游标、未决操作、结果和事件 | 任务模板或设备本身的真实状态 |

`VersionedCode` 用 `code + version` 确定方法、插件、规程、算法及规则身份。相同编码不同版本不能静默互换。

标准物现在区分波长、透射比和标准溶液的结构：数值量和条件仍用 `Quantity`，元素、基体等使用类别声明的文本/枚举属性，不塞入“特征值”字符串。登记和读取校验结构，规程要求检查适用属性，执行复核比较完整资料快照而非仅 ID。详细结构、兼容方式和未实现的配制/开封管理见 [标准物类型说明](PLUGIN-PLATFORM.md#标准物按类别扩展)。紫外旧工作区仍使用原字段映射，尚未迁移到这套类型化管理 API。

模板展示不参与新业务的计算判定：外部算法结果先保存，运行更新轻量推送，单独的 `report` 命令生成视图。任务固定所选模板，旧任务不会随新布局改变。渲染扩展、前端去重和失败恢复规则见 [计算与展示分离](PLUGIN-PLATFORM.md#计算与模板展示分离)；紫外旧工作簿链路的实际优化与剩余限制见 [紫外工作簿说明](UV-INTEGRATION.md#工作簿计算与推送)。

## 五、当前紫外实现

### 5.1 是否能替代原紫外入口

标准化模式下，当前紫外执行入口已经走完整兼容插件；运行时不继承或委派给原 `ExcelWebSocketHandler`，也不在失败后自动回退到它。

替代的是检定校准 WebSocket 的完整执行入口及其分层组织。原紫外驱动、计算器和管理接口继续使用原实现；数据库可配置切换为独立标准库；执行流程中的任务、模板项目、标准物和项目状态现已通过公共业务服务及原库适配器访问，不再直接依赖这些原实体和 Service。并非把整个紫外项目、数据库和页面全部改成新公共业务实现。

原 Handler 仍保留为 `legacy` 回滚入口。因此“原 Handler 还在生产包里”不代表标准化模式还在调用它，实际选择以本次进程日志为准。

### 5.2 执行链路

```text
/ws/calibration/excel
  → 宿主 InspectionExecutionConfiguration 选择模式
  → PlatformInspectionWebSocketHandler
  → InspectionRuntimeService
  → FullUvInspectionRuntime
      ├── UvInspectionSessions：连接、心跳、状态和曲线推送
      ├── UvInspectionWorkflow：单项、自动、确认和停止
      ├── UvInspectionAcquisition：准备、校零、切池及原驱动调用
      ├── UvInspectionAlgorithms：组织算法输入输出及既有辅助处理
      ├── UvInspectionWorkbook：单元格、公式、判定、工作簿和推送
      └── UvInspectionContext：公共业务/外部适配器、剩余紫外服务及进程内状态
```

此外还有以下适配职责，均在现有 UV 源码包内：

- `FullUvInspectionConfiguration`：只在标准化且仪器族为 UV 时装配兼容插件。
- `UvChannelSession`：将公共通道转换为旧流程所需会话，固定实际任务与操作人。
- `UvSpectrumHistory`：通过公共工作区读写测量记录，只转换紫外曲线格式，保持倒序与坏记录容错；上层决定最多返回四条，不直接引用原实体/数据库服务。
- `UvInstrumentAdapter` / `ExistingUvInstrumentAdapter`：全部 `DevOperationUtilService.operation(...)` 指令改为注入接口，默认原样调用原驱动，含停止指令；不初始化、不重试、不伪造空闲回执。
- `UvAlgorithmAdapter` / `ExistingUvAlgorithmAdapter`：原距离/偏移工具、光谱计算器及 Python 寻峰服务改为注入接口；默认只调用原实现，不新增公式。
- `ExistingUvWorkspaceAdapter`：实现公共 `InspectionWorkspace`，将原任务、模板项目、标准物、资源绑定、项目状态和曲线记录的实体及 MyBatis 条件集中到适配层；JDBC 模式通过兼容视图落入标准库。
- `UvTemplateRenderer` / `ExistingUvTemplateRenderer`：隔离原模板服务的单元格写入方法，沿用原布局、定位和公式工具，不实现新的报告引擎。
- `UvWorkbookStore` / `ExistingUvWorkbookStore`：隔离原工作簿缓存、加载、编辑锁、保存提交和高亮元数据；宿主可替换存储实现，POI 不进入公共 core。

宿主可以提供自己的适配器 Bean，由默认装配让位。Python 调用保留 30 秒等待、任务停止检查和中断处理；取消本地等待不等于远端计算已终止。工作簿/曲线默认存储后端仍复用原服务，但流程已不直接依赖它们；设备管理、辅助计算和异步执行仍保留原依赖，不能将适配器注入理解为业务已完全独立。UV 驱动/算法接口使用旧请求类型，原吸业务插件应使用公共外部能力契约，而不是复制它们。

#### 公共工作区如何与旧库解耦

调用方向为 `UvInspection* → InspectionWorkspaceService → InspectionWorkspace → ExistingUvWorkspaceAdapter → 原服务/Mapper → 所选旧库或标准库兼容视图`。

`InspectionWorkspaceSnapshot` 是旧资料的读取投影，不是数据库实体，也不是新增一套版本化任务/运行模型。公共层不解析紫外 JSON、不把模板编号冒充规程版本、不重新解释标准值精度。参数映射顶层只读，插件不得修改嵌套值。

公共规则包括默认任务操作人校验、模板项目归属（包含单项检测）、资源角色与重复记录校验、标准物选择时存在/启用/有效期及类别检查。默认资源按项目整体覆盖：任务已有该项目任一角色，就完全排除该项目默认资源；只查询本模板未覆盖的项目。截止日当天可选择，旧资料缺少有效期不等于证书已复核。

任务开始、设备绑定或标准物保存返回失败时，不继续后续分派；项目结果更新失败会告警。资源更新失败不再作为“无记录”盲目插入；编辑锁获取失败不更新绑定和工作簿。原库事务不等于跨进程唯一索引，也不能覆盖工作簿缓存和前端推送。

这是业务资料边界的迁移，不是公共 `BusinessRun` 执行闭环迁移。原吸新开发仍使用业务插件和 `InspectionStorage`；只有兼容既有旧数据/旧协议时，才需要提供自己的 `InspectionWorkspace`，不需要复制紫外适配器。

#### 曲线保存与工作簿保存的区别

曲线经 `UvSpectrumHistory → InspectionWorkspaceService → InspectionWorkspace` 保存。公共层核对项目归属、返回记录范围和保存结果，原始字符串不裁剪、不改精度；仪器插件负责格式转换。默认适配器生成原格式 ID、写入时间并调用原曲线服务。历史记录缺失 ID/时间或载荷时不伪造资料，坏 JSON 仍由紫外协议层转换为空数据记录。

曲线保存失败不重试，也不重新下发测量；实际异步项目返回失败，测量成功状态延迟到曲线保存调用成功后才发布。该保护不回滚已经修改的工作簿，不提供跨存储事务或可靠证据链。

工作簿经 `UvWorkbookStore` 加载和提交保存。`WorkbookCacheManager` 在锁内冻结字节快照，`UvWorkbookSaveQueue` 串行执行数据库事务；`SUBMITTED` 是提交请求，`workbook_save/COMMITTED` 才表示事务完成，回执与内容一起落库。失败为 `FAILED`，历史无回执为 `UNCONFIRMED`，可单独重试保存但不重测。前端及数据库升级步骤见 [前后端部署与兼容](UV-INTEGRATION.md#前后端部署与兼容)。

工作簿拥有独立的提交回执，但不是整个检定任务的单一事务。工作簿、曲线、项目结果和前端消息不在同一事务中，设备管理和停止也尚未迁入公共运行状态机。

### 5.3 保留的紫外协议

| `type` | 业务含义 | 保留行为 |
| --- | --- | --- |
| `0` | 单项检测 | 原参数校验、准备、测量、计算及保存 |
| `1` | 自动检测 | 原项目排序和自动调度；保留仅允许多池的限制 |
| `2` | 标准物选择 | 原工作簿更新和保存 |
| `3` | 历史曲线查询 | 原顺序、最多四条及坏记录容错 |
| `4` | 人工确认 | 原暂停恢复和重复确认拦截 |
| `5` | 质量线编辑 | 原工作簿求值和保存 |
| `close` | 停止请求 | 原停止分支，不向另一套实现重发 |

握手时，旧 `default` 任务别名会解析为该操作人的实际任务，之后固定在连接内。消息不能借修改 `taskId/updateBy` 改变连接身份。

光谱、时间、光度与单池/多池的六组采集分派、参数限制及型号分支仍按旧实现执行。保留分派不意味着扩大驱动支持型号，也不意味着每种型号都支持所有组合。

### 5.4 紫外兼容路径的限制

- 暂停和停止仍沿用兼容语义；工作簿异步保存已增加快照及事务回执，仍未迁入公共业务状态机。
- 保留进程内任务状态，不提供重启续测、跨进程设备锁或断电恢复。
- 本地停止标记、清空队列、停止分支返回都不能证明仪器已空闲。
- 前端推送成功、工作簿缓存更新和数据库保存不是同一事务。
- 连接身份检查不能替代完整的宿主授权系统。

正式启用必须用真实页面、实际支持型号、数据库和最终报告做验收，不能只根据本次编译通过就宣布所有现场行为已验证。

## 六、公共业务状态机

### 6.1 基本原则

每条命令只推进一个业务边界，没有后台自动执行循环。客户端根据返回状态决定下一步，不得持续发送 `advance` 代替状态判断。

`start` 创建运行并占用设备，但不下发采集。实际提交由后续 `advance` 触发。每次状态变化产生新快照、增加 `revision`，再由宿主仓储比较旧修订号后保存。

### 6.2 状态含义

| 状态 | 含义 | 下一步及约束 |
| --- | --- | --- |
| `READY` | 已到安全边界 | 可以 `advance`，也可以在无未决操作时取消 |
| `WAITING_FOR_OPERATOR` | 等待人工确认 | `confirm` 后回到 READY，不自动测量 |
| `DISPATCHING` | 已保存提交意图，正调用驱动 | 不能重放或假设已停止 |
| `WAITING_FOR_INSTRUMENT` | 驱动已接受请求，等最终回执 | 使用 `poll` 查询或请求停止 |
| `CALCULATING` | 正调用外部算法，结果尚未归档 | 不能并发重算或直接假设停止完成 |
| `STOPPING` | 已请求停止，尚未确认空闲 | 持续保留占用，`poll` 确认 |
| `UNCERTAIN` | 存在未决设备操作，结果未知 | 核对原请求和真实设备；不得盲目重发，可按契约请求停止 |
| `COMPLETED` | 所有项目结果已归档 | 终态；不表示所有计量判定合格 |
| `FAILED` | 运行失败且无未决设备操作 | 终态；不等同结果中的不合格判定 |
| `CANCELLED` | 安全边界取消或确认停止空闲 | 终态 |

`itemIndex`、`stepIndex` 从 0 开始。完成时项目游标等于项目总数，不能把该值当成仍可执行的项目下标。

### 6.3 典型流程

```text
start → READY
          ├─ advance 到确认步骤 → WAITING_FOR_OPERATOR
          │                         └─ confirm → READY
          ├─ advance 到设备步骤 → DISPATCHING → WAITING_FOR_INSTRUMENT
          │                                     ├─ poll 未完成 → 保持原状态
          │                                     ├─ poll 完成且空闲 → READY
          │                                     └─ stop → STOPPING
          │                                                 └─ poll 确认空闲 → CANCELLED
          └─ advance 到项目采集结束 → CALCULATING
                                      └─ 结果归档 → 下一项目 READY 或 COMPLETED
```

驱动异常且操作未决时可能进入 `UNCERTAIN`。驱动明确失败且空闲、算法失败且没有未决设备操作等情况可能进入 `FAILED`。

### 6.4 提交、回执、计算和保存的边界

1. **先保存提交意图，再调用驱动。** 请求 ID 必须在实际下发前确定并保留。
2. `submit` 正常返回只表示驱动调用返回，不表示采集完成。
3. `poll` 最终回执必须与原请求 ID 和仪器 ID 一致；测量完成还需要原始数据引用。
4. `requestStop` 只表示请求停止；只有后续外部确认停止且空闲才能取消并释放占用。
5. 调用算法前保存计算中状态，校验结果的请求 ID、项目 ID、算法及规则版本后再归档。
6. 保存冲突或持久化失败不能被当成普通设备失败自动重试；外部操作可能已经发生，须先核对状态。

一次命令可能保存多个中间状态，`revision` 不保证每条命令只增加 1。客户端必须使用响应中的最新值。

### 6.5 并发和版本

运行时的 `synchronized` 只串行化本进程请求。跨进程互斥、原子占用、修订号比较和释放设备必须由正式仓储实现。

运行固定插件版本和编排版本，算法和判定规则也使用精确版本。插件版本变化后，公共路径允许查询旧运行，但拒绝继续执行旧运行的状态修改，必须先核对。不能把 `SNAPSHOT` 构件版本误认为业务插件版本可以随意变化。

## 七、原吸和其他仪器如何接入

### 7.1 复用什么、增加什么

复用 core 和 starter；增加正式仪器插件及宿主适配。不要复制紫外六个流程类、旧 Handler、测试驱动或内存数据库。

以原吸为例，项目可采用：

```text
原吸宿主项目
  ├── 依赖 metrology-spring-boot-starter
  ├── 依赖团队正式原吸插件
  ├── 提供已有原吸驱动和算法适配 Bean
  ├── 提供 InspectionStorage、InspectionAccess
  └── 提供认证、前端、数据归档及现场安全措施
```

原吸插件可以是独立 Maven 工程，也可以放在 `instruments/aas` 并显式配置其构建。当前仓库只有测试用原吸示例，没有正式原吸生产插件。

### 7.2 需要实现的插件契约

实现 `BusinessInspectionPlugin`。以下签名摘自当前接口，不是需要修改公共接口的清单：

```java
PluginDescriptor descriptor();
List<MeasurementMethod<?>> measurementMethods();
List<ExecutionMethod> executionMethods();
List<InspectionTemplate> templates();
List<MaterialType> materialTypes();
List<InspectionReportRenderer> reportRenderers();
InstrumentGateway instruments();
ExternalInstrumentOperations operations();
ExternalAlgorithms algorithms();
```

| 插件内容 | 正式原吸项目需要做的工作 |
| --- | --- |
| 描述符 | 定义唯一插件 ID、业务版本、仪器族 `AA`、名称、平台 API 版本 1 |
| 参数 | 实现 `MethodParameters`，明确本方法实际需要的参数及约束 |
| 测量方法 | 实现 `MeasurementMethod<T>`，提供方法版本、参数类型及只读采集规划 |
| 执行方法 | 实现 `ExecutionMethod`，编译确认、准备、测量步骤，并固定算法和规则版本 |
| 模板和规程 | 提供实际项目顺序、资源要求和布局引用；不是直接使用测试三点示例 |
| 设备身份 | 查询真实仪器 ID、仪器族和实际支持能力 |
| 操作适配 | 转换平台请求为已有驱动调用，保留原请求身份和停止确认语义 |
| 算法适配 | 调用已有算法/判定服务，转换输入与输出，不重新写公式 |

方法规划和流程编译不能操作仪器。点火、熄火、燃气联锁及其他现场安全能力由设备团队负责，只有真实可用并经过验证的操作才能被声明为步骤。

### 7.3 注册和装配

正式插件 JAR 的 `META-INF/spring.factories` 注册自动配置类，例如：

```properties
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
com.persee.workstation.aas.metrology.AasMetrologyConfiguration
```

这里的类名是说明性示例，正式项目必须提供对应类及真实插件 Bean。配置类可参考现有测试示例的 `@AutoConfigureBefore(MetrologyAutoConfiguration.class)` 和具名外部适配器注入方式，但不要保留测试专用 profile 或假实现作为生产配置。

插件注册时必须满足：

- 插件 ID 唯一，同一仪器族只有一个插件。
- 只能选择业务契约或兼容契约之一，不能同时实现两种。
- 平台 API 版本与当前版本 1 一致。
- 方法、模板、操作、算法等定义齐全且版本匹配。
- 宿主配置内置 JDBC 仓储（或提供自定义仓储）、权限和外部服务依赖；缺少时拒绝启动。

### 7.4 原吸宿主依赖与配置

```xml
<dependency>
    <groupId>com.persee.workstation</groupId>
    <artifactId>metrology-spring-boot-starter</artifactId>
    <version>0.1.0-SNAPSHOT</version>
</dependency>
```

starter 已依赖 core。还需加入团队正式插件及已有驱动、算法所需依赖；它们没有可以直接套用的统一 Maven 坐标。

```yaml
metrology:
  inspection:
    mode: standardized
    instrument-family: AA
```

不是把 UV 改成 AA 就完成接入。配置要求实际已安装 AA 插件及所有正式适配器。当前按一个仪器族选择一个运行时，同族设备通过任务中的 `instrumentId` 区分；不支持运行中热插拔。

### 7.5 建议落地顺序

1. 与仪器团队确认已有身份查询、能力查询、提交、回执、停止和空闲确认接口。
2. 确认正式规程、参数、标准物要求、算法和判定规则版本。
3. 编写参数、方法规划、执行配方、模板和插件描述符。
4. 编写调用已有能力的适配器，而不是重写底层驱动或算法。
5. 接入正式仓储及认证授权，验证事务、设备占用和版本比较。
6. 注册插件并配置 AA，先运行无真机的契约测试。
7. 对接公共管理和 WebSocket 协议，前端按实际状态推进。
8. 由仪器团队完成真实设备、结果、报告、停止及安全验收后再上线。

## 八、宿主外部接口与持久化要求

### 8.1 外部能力接口

| 接口 | 谁实现 | 核心要求 |
| --- | --- | --- |
| `InstrumentGateway` | 仪器适配器 | 返回真实身份、仪器族和版本化能力快照 |
| `ExternalInstrumentOperations` | 已有驱动的业务适配器 | 短时提交/查询/停止，保留请求 ID，不把未知结果当成功 |
| `ExternalAlgorithms` | 已有算法服务的适配器 | 检查精确版本，返回关联身份、指标、判定和证据引用 |
| `InspectionStorage` | 宿主 | 按仪器族提供标准物、目录和运行仓储 |
| `InspectionWorkspace` | 旧资料宿主适配器 | 中立读取投影、定向资料更新和测量记录查询/追加；只用于渐进迁移，不替代运行仓储或占用契约 |
| `ReferenceMaterialRepository` | 宿主仓储 | 保存和查询真实标准物资料 |
| `BusinessCatalogRepository` | 宿主仓储 | 保存规程版本及任务，不静默覆盖相同身份 |
| `BusinessRunRepository` | 宿主仓储 | 原子创建并占用、比较修订号更新、确认终态释放占用 |
| `InspectionAccess` | 宿主权限服务 | 基于已认证身份检查目录和任务访问 |
| `InspectionChannel` | 通信接入层 | 安全发送及关闭通信；关闭不等于设备停止 |
| `InspectionRuntime` | 平台或兼容插件 | 定义命令、任务解析、连接和执行生命周期 |

### 8.2 设备请求和回执

驱动适配必须保留 `DeviceOperation` 中的请求 ID、运行 ID、仪器 ID、操作人、项目与步骤信息。`submit` 异常时，原操作也可能已经执行，不能通过新建请求 ID 再发一次来“补救”。

回执分为 `PENDING`、`COMPLETED_IDLE`、`FAILED_IDLE`。最终回执必须代表设备已空闲；测量完成还必须提供原始数据引用。停止接口需要把“停止请求已发送”和“原操作确实停止且空闲”区分开。

外部原始数据和计算证据应由宿主归档，平台使用引用关联。引用指向何种文件、对象存储或数据库由宿主确定。

### 8.3 仓储不是简单 CRUD

`BusinessRunRepository` 的关键要求：

```java
void createAndReserve(BusinessRun run);
Optional<BusinessRun> findRun(String runId);
void compareAndSave(long expectedRevision, BusinessRun run);
```

- `createAndReserve` 必须在同一个原子边界创建运行并占用仪器；运行 ID 重复或设备已有未终结运行时拒绝。
- `compareAndSave` 必须比较旧修订号；冲突按契约抛出 `ConcurrentModificationException`，不能无条件覆盖。
- 只有保存已确认终态时才能释放占用；`STOPPING/UNCERTAIN` 仍保留。
- 读取和保存的快照不能因共享可变对象而绕过版本控制。
- 跨进程事务及互斥必须由真实仓储保证，不能仅依赖 Java 对象锁。

平台已经提供 `docs/sql/metrology_standard.sql` 作为公共 MySQL 5.7 初始化脚本，并由 starter 提供默认 JDBC 生产仓储。脚本中的公共表供新仪器共用，内置紫外快照只服务当前项目兼容恢复；原吸插件不依赖紫外兼容视图，也不需要另建一套业务表。

### 8.4 权限和身份

新仪器公共管理及业务 WebSocket 依赖宿主已认证的 `Principal`。`updateBy` 必须与登录身份一致，它不是独立认证凭据，也不是只填用户名就获得权限。

每次公共业务执行重新校验任务访问权限，并检查运行属于当前任务及操作人。目录管理也调用权限适配器。没有正式权限服务时不能以“默认允许”作为生产实现。

紫外兼容连接保留旧接入方式，不能把这套兼容行为误认为已经获得完整的新业务鉴权保障。

## 九、公共 REST 接口

### 9.1 接口范围

| 方法与路径 | 用途 | 访问要求 |

| `GET /api/metrology/plugin` | 当前插件描述符 | 已认证身份 |
| `GET /api/metrology/templates` | 只读模板目录 | 目录权限 |
| `GET /api/metrology/material-types` | 标准物类别结构、类型版本与允许属性 | 目录权限 |
| `POST /api/metrology/materials` | 登记标准物 | 目录权限 |
| `GET /api/metrology/materials/{id}` | 查询标准物 | 目录权限 |
| `POST /api/metrology/tasks` | 从模板及标准物绑定创建任务 | 目录权限 |
| `GET /api/metrology/tasks/{id}` | 查询任务 | 对应任务权限 |

除插件信息外，这些公共业务管理接口面向 `BusinessInspectionPlugin`。紫外兼容插件继续使用原管理接口，尝试调用不支持的公共业务管理能力会返回 501。

当前没有标准物列表分页、模板编辑发布或完整公共管理页面接口。结果展示通过 WebSocket `report` 命令提供默认结构化视图及插件渲染扩展，不是任意模板引擎。不要把 core 的内部服务方法直接当成已经提供的 HTTP API。

### 9.4 错误处理

当前控制器明确处理：无认证身份 401、权限拒绝 403、输入校验类异常 400、兼容路径不支持的能力 501。其他宿主异常按现有异常处理机制返回，不提供覆盖全部情况的统一业务错误码规范。

前端不能只凭 HTTP 通信成功认定已创建任务，应检查实际响应。参数错误、资源缺失或版本不匹配应先修正资料，不应自动重复下发设备操作。

## 十、公共 WebSocket 协议

### 10.1 连接和身份

新仪器业务路径使用：

```text
/ws/calibration/excel?taskId=实际任务ID&updateBy=当前登录操作人
```

宿主必须已经建立认证身份，`updateBy` 必须与 `Principal` 一致。连接固定任务及操作人；同一连接不能在后续命令里切换成另一个任务或用户。

公共业务插件要求具体任务，不使用旧紫外 `default` 别名。旧紫外继续按原页面和兼容协议连接。

### 10.2 命令表

| 命令 | 必要字段 | 行为 |
| --- | --- | --- |
| `start` | `type/runId` | 从当前任务准备计划，创建运行并占用仪器，不采集 |
| `advance` | `type/runId/revision` | 在 READY 推进到确认、设备操作或外部计算 |
| `confirm` | `type/runId/revision` | 确认当前人工步骤，回到 READY |
| `poll` | `type/runId/revision` | 查询正在等待的设备回执，或停止空闲确认 |
| `stop` | `type/runId/revision` | 安全边界取消，或请求停止原未决操作 |
| `status` | `type/runId` | 查询当前已存快照，不推进状态 |
| `report` | `type/runId` | 只读生成已保存快照的展示；失败可单独重取，不重新计算 |

修改命令中的 `revision` 必须是整数，且与最新快照一致。`runId` 由调用方为本次运行确定且应唯一，重复 `start` 不会被当成一次新的合法采集。

### 10.3 消息和响应示例

```json
{"type":"start","runId":"run-001"}
```

成功创建运行后的响应结构示意：

```json
{
  "type": "run",
  "plugin": {"code": "persee.aas.inspection", "version": "1"},
  "taskId": "task-001",
  "runId": "run-001",
  "revision": 0,
  "status": "READY",
  "itemIndex": 0,
  "stepIndex": 0,
  "results": []
}
```

响应中的插件、游标、版本和结果以实际插件及运行快照为准。连接初始化还会发送 `type=connected`、插件描述符和实际任务 ID。

运行响应另带 `protocolVersion=1`、`eventId`、`template` 和 `renderer`。修改命令返回的快照同步通知同任务同操作人的连接，`status/report` 只回给请求者；单连接失败不阻断其他连接。前端按 `runId/revision` 识别旧消息，不得通过重发测量命令补丢失消息。

`{"type":"report","runId":"run-001"}` 返回 `type=report`、相应修订号和 `document.mediaType/content`；默认内容是 JSON 结果列表字符串，其他媒体类型由插件扩展。`complete` 表示全部项目是否完成，不是证书签发或报告已落库的标志。渲染失败返回 `type=report_error`、`code=REPORT_RENDER_FAILED`，业务状态保持不变。完整契约见 [展示接口](PLUGIN-PLATFORM.md#计算与模板展示分离)。

后续消息形式：

```json
{"type":"advance","runId":"run-001","revision":0}
```

```json
{"type":"confirm","runId":"run-001","revision":1}
```

```json
{"type":"poll","runId":"run-001","revision":4}
```

```json
{"type":"stop","runId":"run-001","revision":5}
```

```json
{"type":"status","runId":"run-001"}
```

这些消息只说明字段格式，不是一套可连续照抄的真实规程。每次使用上次实际响应的修订号和状态。

### 10.4 修订号为何可能跳变

对于“单项目、一个确认步骤、一个采集步骤”的说明性流程，默认编排可能出现：

| 当前动作 | 结果状态 | 修订号示意 |
| --- | --- | --- |
| `start` | READY | 0 |
| `advance` 进入人工确认 | WAITING_FOR_OPERATOR | 1 |
| `confirm` | READY | 2 |
| `advance` 提交设备 | WAITING_FOR_INSTRUMENT | 4，包含提交中和等待两个保存阶段 |
| `poll` 得到完成且空闲回执 | READY | 5 |
| `advance` 调用算法并归档最后项目 | COMPLETED | 7，包含计算中和结果归档两个阶段 |

真实原吸流程可能含多个确认、准备、采集及项目，不能固定使用这组数值，也不能把这个说明性流程当作安全操作规程。

### 10.5 错误、断线和重连

- 握手失败会尝试返回错误并关闭连接；命令失败会返回错误，不向旧实现回退。
- 命令已改变状态但响应发送失败时，外部操作可能已经发生，不能据此重新 `start` 或重复提交。
- 公共业务路径断线只移除通知通道，不取消运行、不释放设备；重连先查询 `status`。
- 状态查询仍需相同任务及操作人权限，不能用另一个任务连接读取不属于它的运行。
- 插件版本改变后可查询旧运行，但不能未经核对继续修改状态。
- STOPPING 未确认空闲、UNCERTAIN 未核对原请求时，不能通过清理内存或重启来假定设备已安全释放。

实际通信错误还需检查宿主网络、认证和进程状态，不能把前端断开等同仪器停止。

## 十一、配置、模式切换与回滚

### 11.1 当前紫外宿主配置

`src/main/resources/application.yml` 当前包含：

```yaml
metrology:
  inspection:
    mode: ${METROLOGY_INSPECTION_MODE:standardized}
    instrument-family: UV
```

因此该文件未被其他配置覆盖时，环境变量未设置会选择标准化模式。**这只是默认配置，不代表某个已经运行的现场进程已切换；必须看该进程的实际日志。**

| 配置 | 当前紫外宿主选择 |
| --- | --- |
| `mode=legacy` | 原 `ExcelWebSocketHandler` |
| `mode=standardized` 且 `instrument-family=UV` | 公共入口及完整 UV 兼容插件 |
| 未知模式、缺失/重复入口、就绪检查失败 | 拒绝启动，不自动降级 |

宿主属性类自身有缺省值，公共自动配置也有自己的条件缺省值；不能脱离宿主 YAML 和实际启动配置，仅根据某个类的缺省值判断当前模式。新仪器宿主应显式配置模式与仪器族。

### 11.2 环境变量示例

在启动应用的 PowerShell 环境中选择回滚模式：

```powershell
$env:METROLOGY_INSPECTION_MODE='legacy'
```

选择标准化模式：

```powershell
$env:METROLOGY_INSPECTION_MODE='standardized'
```

随后按宿主既有启动方式启动新进程。设置当前终端环境变量不会修改另一个已经启动的服务进程。

### 11.3 安全切换顺序

1. 停止新任务进入，核对当前运行和未决设备操作。
2. 按现有现场流程处理测量、确认停止及设备实际空闲。
3. 保存需要留存的数据、工作簿和报告，核对数据库状态。
4. 设置目标模式并重启宿主。
5. 核对本次进程的模式选择、插件装配和正常启动日志。
6. 再验证页面连接、任务和工作簿初始化，按验收流程恢复业务。

不是热切换，也不是编辑 YAML 后自动把在途任务迁移到另一套运行时。原吸独立宿主仅引入 starter 不会自动获得一个旧原吸 Handler；如要提供 legacy 回滚，必须由该宿主另行实现原入口和开关装配。

### 11.4 Maven 测试开关不是业务开关

`-Pmetrology-tests` 是 Maven 测试 profile，控制是否编译并运行 UV 回归；不改变应用的 `legacy/standardized` 运行模式。

测试示例的 Spring profile 只在测试 classpath 使用，也不是启用真实原吸的生产开关。

## 十三、日志说明

### 13.1 先看模式，再看任务

先搜索 `[检定校准]`，确认本次进程的模式及插件；再按 `sessionId → taskId → runId → requestId` 关联执行。UV 兼容日志通常按任务和项目定位，不保证拥有公共运行 ID。

```text
示意：
[检定校准][插件装配] family=UV, plugin=persee.uv.compatibility@1, ... kind=COMPATIBILITY
[检定校准][执行结果] mode=STANDARDIZED, kind=SHARED_BUSINESS, family=AA, ... from=READY, to=WAITING_FOR_INSTRUMENT, ...
```

上面只是字段示意，不是某一现场进程的运行记录。

### 13.2 主要日志

| 标记 | 级别 | 正确理解 |
| --- | --- | --- |
| `[模式选择]`、`[插件装配]` | INFO | 进程选中哪套入口、仪器族、插件版本和路径类型 |
| `[紫外外部能力装配]`、`[公共编排装配]` | INFO | 实际驱动/算法适配器及来源、编排器及版本；不把紫外兼容流程称为公共状态机 |
| `[紫外业务工作区装配]` | INFO | 公共业务服务、实际资料适配器和模板渲染来源 |
| `[紫外业务资料写入]` | INFO/WARN/DEBUG | 操作、任务/项目及 `repositoryAccepted`；失败 WARN、时间戳成功 DEBUG，不证明事务已提交或测量已完成 |
| `[紫外存储装配]`、`[紫外工作簿写入]`、`[工作簿保存]` | INFO/WARN | `SUBMITTED` 为提交请求，`COMMITTED` 为事务完成，`FAILED` 为失败；无历史回执时为 `UNCONFIRMED` |
| `[紫外布局读取异常]` | WARN | 可选布局元数据查询/解析失败，兼容返回空映射，不输出完整内容 |
| `[外部驱动调用]`、`[外部算法调用]` | DEBUG/WARN | 原调用返回或异常类型；不记录完整指令/曲线正文、不自动重试 |
| `[连接路由]`、`[连接关闭]` | INFO | 连接实际交给谁及关闭码，不是设备启动/停止证明 |
| `[会话绑定]`、`[会话解绑]` | INFO | 公共业务通道与任务关系；解绑不自动取消运行 |
| `[标准物登记]`、`[任务创建]` | INFO | 管理服务成功返回；创建不等于已经测量 |
| `[执行结果]` | INFO/WARN/DEBUG | 状态推进 INFO，失败/未知结果 WARN，无变化查询和轮询 DEBUG |
| `[紫外会话绑定]`、`[紫外会话解绑]` | INFO | 兼容通道关系，不等同设备就绪或空闲 |
| `[紫外命令]`、`[紫外命令返回]` | INFO/DEBUG | 命令接收与分派返回分开，历史查询仅 DEBUG |
| `[紫外项目开始]`、`[紫外项目结束]` | INFO | 原异步流程进出，结束不代表计量合格或全部异步保存完成 |
| `[紫外本地停止]`、`[紫外停止请求]` | INFO | 本地标记/队列处理或旧停止分支返回，不冒充空闲确认 |
| `[紫外历史数据异常]` | WARN | 某历史记录解析异常；定位记录并保留原容错返回 |
| `[请求失败]`、`[管理请求拒绝]` | WARN/ERROR | 拒绝或故障的阶段、类型、代码位置，不自动回退或重发 |
| `[传输异常]`、`[错误通知失败]` | ERROR/WARN | 连接或通知故障，不能据此重复设备命令 |

### 13.3 公共执行定位字段

`mode/kind/family/plugin/sessionId/taskId/runId/instrumentId/command/from/to/revision/itemIndex/stepIndex/requestId/resultCount/elapsedMs`。

其中 `elapsedMs` 是该命令处理耗时，不是整项仪器采集时长；`resultCount` 是结果数量，不是合格数量。`COMPLETED`、`STOPPING`、`UNCERTAIN` 按状态机定义解释，不能只凭中文“完成/停止”字样判断现场状态。

### 13.4 日志级别和内容

生产默认关注 INFO，只有排查轮询或分派返回时临时打开相关类 DEBUG：

```yaml
logging:
  level:
    com.persee.workstation.metrology.boot.BusinessPluginRuntime: DEBUG
    com.persee.workstation.uv_inexus.metrology.fulluv.FullUvInspectionRuntime: DEBUG
```

紫外项目日志在 `UvInspectionWorkflow`；公共失败日志在 `PlatformInspectionWebSocketHandler`；原紫外宿主模式/消息路由 logger 是 `InspectionExecutionConfiguration`，独立 starter 的装配/路由 logger 是 `MetrologyAutoConfiguration`。

排查后恢复 INFO，避免长期打开整套驱动 DEBUG。新增标准化日志不打印请求正文、完整 URI、证书内容、曲线或算法结果正文；可变字段移除控制字符并限长，异常采用类型及代码位置定位。

原紫外其他历史日志仍沿用旧实现，不能把整个宿主日志当成已经完成全面脱敏的审计系统。日志只是定位手段，不能替代运行仓储、证据和现场确认。

## 十四、常见问题与排查

| 现象 | 优先检查 | 不应采取的做法 |
| --- | --- | --- |
| 配成 standardized 后不能启动 | 仪器族、插件是否安装、入口是否重复、依赖及就绪检查 | 删除校验或静默退回旧入口 |
| 不知道当前用哪套 | 本次进程 `[模式选择]` 和 `[插件装配]` | 只看 YAML 或旧进程日志 |
| 原吸配置 AA 后无插件 | 是否有真实插件 JAR/Bean、自动配置及全部适配器 | 把测试原吸示例打进生产包 |
| 缺少仓储/权限/驱动 | 宿主 Bean 和插件构造注入 | 提供默认 true、空返回或内存替身蒙混启动 |
| 连接后权限失败 | 登录 Principal、updateBy、任务归属及权限适配 | 仅修改 URL 的操作人字段冒充身份 |
| revision 冲突 | 查询最新运行，核对之前命令是否已执行 | 自动改成新修订号重放旧命令 |
| WAITING_FOR_INSTRUMENT 一直不变 | 查询原请求回执、设备状态及数据引用 | 重发采集或直接视为完成 |
| STOPPING 一直不变 | 停止是否真实执行、空闲确认是否可用 | 清掉占用或强行写终态 |
| UNCERTAIN | 原请求身份、真实设备、仓储中记录的原因和操作结果 | 新建请求 ID 自动重试 |
| COMPLETED 但结果不合格 | 外部判定结果及证据 | 把完成状态等同计量合格 |
| 前端断线后任务仍在 | 公共业务断线不取消，先查询状态 | 用断线作为设备停止依据 |
| UV 命令返回但数据未保存 | 原异步任务、工作簿缓存、数据库和报告链路 | 把分派返回当作所有保存完成 |
| 历史曲线含坏记录 | 按异常日志定位 recordId，检查原记录 | 吞掉后续有效曲线或打印整段敏感数据 |
| UV 下公共管理返回 501 | 是否错误调用业务插件专用接口 | 以此认定原紫外标准物管理消失 |

处理未知设备结果或持久化异常时，应先保留原请求和证据，再按仪器团队流程核对，不以重启、切换模式或清理目录代替现场确认。

## 十五、维护和上线验收

### 15.1 改动放在哪里

| 变更 | 建议位置 |
| --- | --- |
| 公共状态、不变量、资源约束 | core 的 `domain/application` |
| 公共入口、装配、日志和权限接入 | starter |
| 当前 UV 兼容流程 | uv 对应职责层，保持旧协议和回滚入口 |
| 新仪器参数、规程、方法、模板 | 新仪器正式插件 |
| 驱动、算法协议转换 | 对应已有服务的适配器 |
| 数据库事务、占用、鉴权、证据 | 宿主正式实现 |

六个 `UvInspection` 类是普通维护源码，不再依赖生成器。修改采集、计算、保存或停止必须补对应回归并核对真实结果，不以单纯代码分层等同运行时等价证明。

### 15.2 软件检查

- 公共模块和宿主构建通过，测试报告无失败/错误。
- 插件身份、仪器族和 API 版本唯一且一致。
- 缺失正式依赖时失败，不静默使用测试替身。
- 生产 JAR 不包含测试插件、假驱动或测试仓储。
- 旧 UV 页面协议与明确的 legacy 回滚入口保留。
- 日志可关联运行，不刷高频 INFO、不将未知结果写成成功。

### 15.3 紫外现场验收清单

- 实际页面连接、任务别名解析、操作人、工作簿及历史曲线正确。
- 标准物选择、模板、质量线、公式和最终报告符合原业务。
- 在实际支持型号上验证光谱/时间/光度及相应单池/多池分支。
- 验证自动多池排序、暂停、确认和重复指令行为。
- 验证停止、断线重连、数据库保存和需要归档的报告。
- 对异常、超时、停止和保存语义做现场核对，再验证安全回滚流程。

### 15.4 原吸现场验收清单

- 正式规程、参数、标准物及算法版本经仪器团队核对。
- 身份和能力来自真实设备，不是测试固定值。
- 准备及采集操作由正式驱动完成，请求和回执可关联。
- 安全联锁、异常和停止空闲确认按设备团队流程验证。
- 重复指令、陈旧修订号、未知回执和保存失败不导致盲目重发。
- 正式数据库中验证原子占用、修订号比较及终态释放。
- 验证原始数据、计算结果、判定证据、报告和权限隔离。
- 前端按状态推进，在断线或异常后先查询，不擅自继续操作。

以上为验收范围，不提供具体设备的危险操作步骤。真机验证应由有资质的仪器团队按现场安全要求执行。

## 十六、能力边界与后续工作

### 16.1 当前不能宣称的能力

1. 所有紫外业务已经进入公共状态机。
2. 真实原吸插件、驱动、算法和生产数据库已联调完成。
3. 无需宿主实现即可提供跨进程设备锁和持久化恢复。
4. 日志已经构成完整计量审计或合规证明。
5. 有了结构化结果和渲染接口，就已经具备模板编辑发布、分页、任意模板渲染和可靠报告归档。
6. 配置支持热切换、插件热插拔或自动迁移在途运行。
7. 旧 UV 页面无需改协议即可运行新的公共业务原吸流程。
8. 所有仪器型号和停止分支都已经完成真机验收。

### 16.2 后续任务按目的推进

| 目标 | 尚需工作 |
| --- | --- |
| 正式使用原吸 | 正式插件、真实外部适配、仓储、权限、前端及安全验收 |
| 更统一的 UV 业务 | 逐项评估迁入公共状态机、数据和协议差异，不只更换入口名 |

## 十七、快速问答

**这套东西是不是又写了一套驱动和算法？**
不是。公共层组织业务，插件调用已有驱动/算法。UV 中保留的是原有适配及辅助处理，不是新的原吸计算实现。

**标准化模式现在是不是还能调用旧 Handler？**
当前 UV 标准化执行走完整兼容运行时，不委派给旧 Handler，也不失败回退；旧 Handler 只保留给 legacy 选择。

**这是不是说明整个 UV 已完成公共化？**
不是。入口和流程已经分层，管理数据及旧执行语义仍保留，尚未全部迁入公共状态机。

**原吸是不是引入 starter 后就能测？**
不是。还需正式插件、已有驱动/算法适配、数据库、权限、前端及真机验收。

**原吸示例为什么放在 test？**
验证公共层没有依赖 UV，且插件装配、状态和日志契约正常；不对应真实规程，不能作为生产插件。

**test 能删吗？**
删掉不会立即让生产包失效，但会失去自动回归保障，不建议删除真实业务测试。

**target 能删吗？**
是构建输出，停止占用进程并归档需要保留的日志后可删除；不要删业务数据和模板。

**这里是不是用 LiteFlow？**
不是，当前用 Java 状态机和默认短步骤编排。也不支持只放入 LiteFlow 依赖就自动替换执行。

**切换后要不要重启？**
要。先处理在途任务及真实设备状态，再配置并重启；不是运行中热切换。

**为什么 stop 返回了还没有完成？**
公共路径需要空闲确认；UV 兼容返回仍遵循原停止语义。通信或分支返回不能证明真实设备已停止。

**为什么 COMPLETED 不等于合格？**
它表示所有项目结果已归档，计量判定由结果中的外部判定及证据决定。

**构建通过是不是就能直接上线？**
不是。构建和替身测试不替代真实数据库、设备、报告和现场安全验收。
